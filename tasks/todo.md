# Недельный план: «Надо сварить» не пересчитывался (2026-08-03)

## Симптом
Владелец: колонка «Надо сварить» не считает «надо − остаток».

## Диагноз
Формула была верной и на боевом ровно та же (сверил скачанный
`varka.kz/manufacture/index.html` с репозиторием — код совпадает; разница в размере
файла — только CRLF/LF). Дело в том, **когда** запускался пересчёт:
1. Поле «Остаток» висело на `onchange` — он срабатывает только при потере фокуса.
   Пока набираешь цифру и смотришь в соседнюю колонку, она стоит на месте.
2. Главное: каждый обработчик ввода дёргал `renderWeekPlan()`, а тот перезаписывает
   `table.innerHTML` — все поля пересоздаются. Замерено на стенде: после `change`
   в ячейке «Надо» прежнее поле «Остаток» отсоединено от DOM, `activeElement` → `BODY`.
   То есть клик, которым пользователь переходил из «Надо» в «Остаток», приходился по
   уже удалённому узлу: фокус терялся, набранное число никуда не попадало, и
   «Надо сварить» оставалось равным «Надо».

## Сделано
- [x] `wpRecalcRow(sku)` — пересчёт вычисляемых ячеек одной строки по `oninput`,
      без перерисовки таблицы. Значения берутся из полей (state на этот момент
      ещё не обновлён — он пишется на `onchange`).
- [x] Обработчики разделены: `oninput` — счёт, `onchange` — запись в state.
      `wpSetStock` больше не вызывает `renderWeekPlan()`.
- [x] `wpBrewCellChanged()` — правка дневной ячейки гасит подсветку «уже сформировано»
      точечно (раньше это делала полная перерисовка).
- [x] `wpRenderGenerateSummary()` вынесена из `renderWeekPlan()` — сводку под кнопкой
      надо обновлять и при точечной правке.
- [x] Проверено на изолированном стенде (копия index.html + локальный статик-сервер,
      `/api` отдаёт 503 → офлайн; боевая MySQL не задействована):
      набор «Надо»=100 → пересчёт сразу; поле «Остаток» переживает уход фокуса с «Надо»;
      «Остаток»=30 → «Надо сварить» 70 ещё до потери фокуса; после `change` в state
      `{JAN-001:30}`; план Пн=90 → «Сварено» 90, итог 20 сразу; правка сформированной
      ячейки снимает ✓ и обновляет сводку; шапка/строка 24 = 24 колонки; формирование
      производства и переключение недель работают. В консоли только ожидаемые
      «[API] сервер недоступен: HTTP 503».
- [x] Запушено (`df8a93a`), сверено на боевом (`Cache-Control: no-cache`, файл свежий).

## Второй заход: «весь столбец не считает» (после `df8a93a`)
Владелец сообщил, что колонка по-прежнему не считает. Нашлось два дефекта данных,
которые на демо-наборе не воспроизводились:
1. **Кавычка/апостроф в названии клиента рвёт inline-обработчик.** `sanitizeUserText`
   обезвреживает только `<` и `>`, а имя клиента подставлялось прямо в
   `onchange="wpSetDemand('...','ТОО "Ромашка"', ...)"`. Замер на стенде по боевой
   версии `df8a93a`: ввод по 4 клиентам → в базу попали только «Каспи» и «Хан Шатыр»,
   по «ТОО "Ромашка"» и «О'Кей» — молча ничего. На экране цифры при этом были, но
   после перерисовки откатывались. Та же дыра была в модалке «Выбрать клиента»
   (`toggleWpClient('${c}')`) — такого клиента нельзя было включить/выключить.
2. **Строка искалась по `data-sku`.** У дубля sku (или отсутствующего sku у старых
   импортированных рецептур) `querySelector` находил только первую такую строку —
   остальные переставали считаться. Воспроизведено на стенде.

Сделано: продукт, клиент и дата больше не подставляются в текст обработчиков —
лежат в `data-*` (через `escapeHtml`), обработчики читают их с самого поля
(`wpDemandChanged` / `wpStockChanged` / `wpBrewCellChanged`, строка — через
`closest('tr')`). То же для тумблеров в модалках выбора клиентов и продукции.

- [x] Проверено на стенде на «злом» наборе (клиенты `ТОО "Ромашка"`, `О'Кей`;
      рецептуры с дублем sku, без sku, с апострофом в sku): все 4 строки считают
      100 − 30 = 70, «Сварено» 55, итог −15; значения совпадают до и после полной
      перерисовки; в базу попали все 4 клиента; тумблеры клиента и продукта работают.
- [ ] Пуш на боевое — ждёт «go» владельца.

## Что стоит уточнить у владельца
Если после этого «Надо сварить» всё ещё «не считает» — вероятно, речь о том, что
колонка «Остаток» пустая по всем строкам и её никто не заполняет руками. Остаток
не подтягивается ниоткуда автоматически (см. ниже) — тогда «Надо сварить» равно
«Надо», и это выглядит как «не считает».

## Не входило в задачу
Остаток хранится глобально по SKU и после формирования производства намеренно не
уменьшается (`index.html`, комментарий у `generateProductionFromWeekPlan`). Если нужно
списание после варки — это отдельная задача.

# Цех не может войти: Варщик и Участок розлива (2026-07-29)

## Симптом
Сотрудники с ролями «Участок варки» и «Участок розлива» сообщили, что их рабочая
ссылка перестала работать — не могут войти и делать свою работу.

## Диагноз (две наложившиеся причины)
1. **Ссылка была старая — GitHub Pages** (`cardexpress1-pixel.github.io/Varka-crm/`).
   Она жива (HTTP 200) и отдаёт ветку `main` эпохи Firebase: `projectId: varka-test`,
   то есть **холодный бэкап, а не боевая система**. Firestore на анонимный REST-запрос
   отвечает 403 → у старой копии больше нет рабочего хранилища, вход там невозможен.
   Значит цех всё это время сидел НЕ в боевой MySQL-системе.
2. **На боевом адресе войти тоже было нечем.** Коммит `43449fd` (2026-07-22, «Единый
   вход через портал») убрал экран входа: все три места без сессии (бут, выход,
   протухшая сессия) делали `location.replace('https://varka.kz/')`. Роли `warshchik`
   и `intake` — локальные роли Производства с логином/паролем, аккаунтов на портале
   у операторов нет → редирект в тупик.
   Сломан был только фронтенд: `api/auth.php`, форма и `doLogin()` всё время целы.

## Сделано

      редиректа. Метка терминала живёт в `localStorage` — после выхода и протухшей
      сессии планшет возвращается к своей форме, а не улетает на портал (иначе ссылку
      пришлось бы открывать заново каждую смену).
- [x] Единая точка выхода `leaveToEntryPoint()` вместо трёх копий `location.replace`
      (бут, `doLogout`, `handleAuthExpired`). Для всех, кроме терминала, поведение
      прежнее — портал.
- [x] На экране входа ссылка «Сотрудникам офиса — вход через портал varka.kz»:
      снимает метку, если `?shop=1` открыли на обычном компьютере.
