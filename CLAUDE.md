# CLAUDE.md — Manufacture (входная точка для исполнителя)

По шаблону `PROJECT_STARTUP_PROTOCOL.md`, Фаза 3 (Ш5), 2026-08-25.

## 1. Проект

Manufacture — производственная система (варка → розлив → отгрузка) для
одной площадки, раздел портала `varka.kz`. Backend: PHP + MySQL (`api/*.php`).
Frontend: монолитный `index.html`, без сборки.
`PLATFORM_CONTEXT_varka.md` **не существует** в этой сессии (Ш0 по платформе
не выполнялся) — не притворяться, что он есть; факты платформы, нужные для
работы, продублированы явно ниже, где это критично.

## 3. Constraint'ы

**Отклонение от целевой модели платформы (не скрывать, не переписывать
задним числом):** проект **ИМЕЕТ** собственный локальный вход и пароли
(`roles.password_hash`, bcrypt) — это не соответствует правилу платформы
«личность только из проверенного портального токена». Зафиксировано как
архитектурное отклонение в `ARCHITECTURE_Manufacture.md` §4 и `ТЗ §5`, не
ошибка этой сессии, требует отдельного решения владельца о миграции.
SSO-токен портала (`verifyPortalToken`) реализован, но как **fallback
после** локальной сессии, не как единственный источник — MFG-003.

**Явно исключено из ТЗ:** не зафиксировано ничего (`TRACEABILITY_Manufacture.md`
§2). Не путать с «Этап 2» (MFG-030, MFG-034 — запланировано, не исключено).

**Конкретно, не абстрактно:**
- Разграничение доступа к `state.php` по роли обязано выполняться на
  сервере (`filterStateJsonForSession()`, `api/state.php`) — скрытие
  пункта меню в UI не заменяет проверку (доказано находкой
  `FINDING_orphaned_zayavki_page.md`: `page-requests` был вне навигации,
  но данные уходили всем ролям, пока сервер не начал их вырезать).
- `state.clients`/`batches`/`workdayHours`/`reactors`/`pouringLines` — то
  же самое НЕ закрыто (открытое техническое решение, ТЗ §5.2). Не считать
  фикс `requests`/`sheetsUrl`/`recipes` образцом «всё разграничено».
- Уровень `viewer` не может писать `state` — проверка в `api/state.php`,
  не только скрытие кнопок на клиенте.
- **MySQL — живая боевая база.** Никогда не проверять/не запускать
  приложение способом, вызывающим запись в неё (включая косвенные —
  смену темы, навигацию: любой такой клик уходит в `POST api/state.php`).
  Проверять только на изолированной копии (свой `api/config.php`, офлайн,
  мок-стейт) — никогда поверх боевой строки `app_state`.
- **Бэкапы `index.html`** — не более 5 в корне; при создании 6-го самый
  старый переносится (не удаляется) в `_archive/index_backups/`.
- **Активная ветка — `migration-mysql`.** `main` — не боевая, легаси
  GitHub Pages/Firebase, не коммитить туда.
- **Не верить «задеплоено» на слово** — сверять `git rev-parse HEAD` на
  сервере с последним коммитом ветки после каждого пуша.
- **`git push` — только с явного «go» пользователя.** Перед пушем
  показать: repo, remote, ветку, `git status`, изменённые файлы, diff.
- **Изоляция от соседних проектов platform varka.kz.** Чтение/запись за
  пределами этого репозитория запрещены deny-правилом в
  `.claude/settings.local.json` (Tracker, varka-kanban, Project_Kanban,
  00Project_portal_varka_kz) — машинно-специфичный конфиг, не в git,
  настраивается заново на каждой новой машине/копии.

## Непрерывность сессий (команды «стоп сессия» / «новая сессия»)
- Пользователь пишет **«стоп сессия»** → обновить `SESSION_STATE.md`: дата; что сделано за сессию; текущее состояние (боевое / в работе, актуальный HEAD); **точные следующие шаги**; открытые вопросы; ссылки (`DASHBOARD_PROGRESS.md`, `tasks/todo.md`, `tasks/lessons.md`). Затем `commit`+`push` **только `SESSION_STATE.md` и другие .md-доки** — код этой командой не пушить, нужен отдельный «go».
- Пользователь пишет **«новая сессия»** → сначала прочитать `SESSION_STATE.md`, пересказать «где остановились», продолжить с «Следующих шагов».
- `SESSION_STATE.md` — держать коротким и актуальным.

Граф кода — `graphify-out/`: `graphify query "<вопрос>"` перед чтением исходников.
