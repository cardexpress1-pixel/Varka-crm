# CLAUDE.md — правила проекта VarKa

## Источник истины и деплой
- **Рабочая копия и источник истины — ЭТОТ репозиторий:** `Desktop/CRM/проект VarKa`
  (remote `origin` = `github.com/cardexpress1-pixel/Varka-crm`).
- **Активная ветка — `migration-mysql`.** Все коммиты идут в неё, боевое = `origin/migration-mysql`.
  Ветка `main` — наследие эпохи GitHub Pages + Firebase: отстала и **НЕ боевая**. Не коммитить в неё
  и не считать её состояние актуальным.
- **Хостинг — Plesk** (тот же аккаунт/VPS, где Tracker). Боевой адрес — **`varka.kz/manufacture`**.
  Старый адрес GitHub Pages (`cardexpress1-pixel.github.io/Varka-crm/`) боевым больше не является;
  жив ли он ещё как статика — **требует уточнения** (не проверено).
- **Деплой автоматический:** правка → `git commit` → `git push origin migration-mysql` → GitHub webhook
  дёргает Plesk Git → сайт обновляется. **Ручной Pull в Plesk не нужен.** Полная процедура развёртывания
  (DNS, БД, конфиг, импорт, смоук-тест) — `docs/DEPLOY_MANUFACTURE.md`.
- `api/config.php` (доступы к БД) **не в git** (в `.gitignore`) — живёт только на сервере, создаётся
  вручную из `api/config.php.example`.
- **Не верить «задеплоено» на слово:** после пуша сверять `git rev-parse HEAD` на сервере с последним
  коммитом ветки.
- **НЕ работать в `Desktop/VarKa`** — это устаревшая копия, не подключённая к git. Все правки — только здесь.
- **`git push` / публикация — ТОЛЬКО с явным подтверждением пользователя («go»).** Перед пушем показать: репозиторий, remote, ветку, `git status`, изменённые файлы, краткий diff.

## Работа с данными (MySQL) — критично
- Приложение подключено к **ЖИВОЙ** MySQL на Plesk через собственный REST API (`api/*.php`).
  Всё состояние — **одна строка в таблице `app_state`** (`id = 1`, поля `data` + `rev`); роли, журнал
  действий и сессии — в соседних таблицах (`roles`, `activity_log`, `sessions`).
  **В приложении нет резервного копирования.**
- **НИКОГДА не запускать/проверять приложение способом, который может вызвать запись в боевую БД.**
  Записью считать не только явный save, но и любые обработчики, дергающие `saveState()` внутри:
  смена темы (`toggleTheme`), навигация, клики — каждый из них уходит в `POST api/state.php`.
- Проверять только на **изолированной копии**: локальный PHP+MySQL со своим `api/config.php`, или
  офлайн (сервер недоступен), или мок-стейт. Никогда — поверх боевой строки `app_state`.
- **Любая запись в общий/внешний ресурс (боевая БД, git push) — только с явного согласия пользователя.**
- Инцидент 2026-07-04 (ещё на Firestore): проверка редизайна поверх живой БД затёрла реальные варки демо-данными; восстановлено реконструкцией из `journalEntries` + `wpGenerated`. Локальная страховка данных — `Desktop/VarKa/recovery/`. Для MySQL правило то же. Подробности — `tasks/lessons.md`.
- **Firebase/Firestore больше не используется:** SDK удалён из `index.html` 2026-07-11, данные перенесены
  через `api/import.php`. Старый проект `varka-test` — холодный бэкап, не трогать и не возвращать в код.
  Оставшиеся в `index.html` имена (`_stateLoadedFromFirestore` и т.п.) — исторические, хранилище давно MySQL.

## Непрерывность сессий (команды «стоп сессия» / «новая сессия»)
- Пользователь пишет **«стоп сессия»** → обновить `SESSION_STATE.md` в репозитории: дата; что сделано за сессию; текущее состояние (что на боевом / что в работе, актуальный HEAD); **точные следующие шаги**; открытые вопросы; ссылки на детали (`DASHBOARD_PROGRESS.md`, `tasks/todo.md`, `tasks/lessons.md`). Затем `commit` + `push` **только `SESSION_STATE.md` и другие .md-доки** (чтобы состояние было доступно в новой сессии на любом устройстве). Код приложения этой командой НЕ пушить — для него по-прежнему нужен отдельный «go».
- Пользователь пишет **«новая сессия»** → ПЕРВЫМ делом прочитать `SESSION_STATE.md`, кратко пересказать «где остановились» и продолжить с раздела «Следующие шаги», не выпадая из контекста.
- `SESSION_STATE.md` — единый документ «где мы остановились». Держать коротким и актуальным.

## Хранение бэкапов index.html
- Хранить в корне не более 5 последних index.html.bak_*.
- Перед созданием нового backup: если бэкапов уже 5 — самый старый
  (по дате в имени файла) переносить (не удалять) в
  _archive/index_backups/.

## Изоляция от соседних проектов platform varka.kz
Чтение и запись за пределами этого репозитория **запрещены явным
deny-правилом** в `.claude/settings.local.json` (permissions.deny,
Read-паттерны на соседние папки: Tracker, varka-kanban, Project_Kanban,
00Project_portal_varka_kz) — это машинно-специфичный конфиг, НЕ
отслеживается git (см. `.gitignore`), а не просто соглашение/договорённость
в документации. Действует только для сессий Claude Code, открытых из
`Desktop/CRM/проект VarKa` (рабочая директория для этого проекта — именно
эта папка, не `Desktop/CRM`). Если открываешь новую сессию на другой
машине/копии этой папки, правило нужно настроить заново.
