# Деплой Manufacture (VarKa) на manufacture.varka.kz — миграция на PHP+MySQL

Ветка: `migration-mysql` (репозиторий Varka-crm). Хостинг: тот же Plesk-аккаунт,
где живёт Tracker (185.98.5.179). Данные для импорта: `CRM/VarKa-local-backup/migration_2026-07-11/`.

Порядок важен: сначала подготовка на сервере, потом импорт, в конце — переключение.
Пока никто не работает в VarKa (окно заморозки) — данные в Firestore не меняются.

## 1. DNS (панель hoster.kz)
- Добавить A-запись: `manufacture` → IP VPS с Tracker (185.98.5.179). TTL обычный.
- Дождаться распространения (`nslookup manufacture.varka.kz` отдаёт нужный IP).

## 2. Plesk: поддомен + SSL + PHP
- Создать поддомен `manufacture.varka.kz`, корень документа — отдельная папка
  (например `manufacture.varka.kz/httpdocs`).
- PHP: версия 8.1+ (как у Tracker), режим FPM.
- SSL: выпустить Let's Encrypt на `manufacture.varka.kz` (или покрыть wildcard,
  если он уже есть). Включить redirect HTTP→HTTPS.

## 3. Plesk: база данных
- Создать БД `manufacture_db` и пользователя с полным доступом к ней.
- Записать host / имя БД / логин / пароль — понадобятся в config.php (шаг 5).

## 4. Git-деплой (как у Tracker)
- Plesk → Git → подключить репозиторий Varka-crm, ветку `migration-mysql`
  (для боевого позже слить в main; сейчас деплоим ветку).
- Целевая папка деплоя — корень поддомена. Сделать Pull.
- ВНИМАНИЕ: `api/config.php` в git отсутствует (в .gitignore) — создаётся вручную.

## 5. Конфиг БД на сервере
- Через Менеджер файлов Plesk скопировать `api/config.php.example` → `api/config.php`.
- Вписать реальные DB_HOST/DB_NAME/DB_USER/DB_PASS из шага 3.
- ALLOWED_ORIGIN оставить `https://manufacture.varka.kz`.

## 6. Проверка синтаксиса PHP (обязательно — локально не проверялось)
На сервере (Plesk → «Запустить PHP-скрипт» или SSH):
```
php -l api/storage.php && php -l api/state.php && php -l api/auth.php \
  && php -l api/activity.php && php -l api/logout.php && php -l api/report.php \
  && php -l api/import.php
```
Все семь должны сказать «No syntax errors». Если ошибка — не продолжать, сообщить мне.

## 7. Импорт данных из Firestore
- Загрузить папку `migration_2026-07-11/` (varka_state.json + activityLog.json) на сервер,
  например в `api/_import/`.
- Запустить CLI-импорт (Plesk «Запустить PHP-скрипт» с аргументами или SSH):
```
php api/import.php api/_import
```
- Ожидаемо: «app_state импортирован, rev …», «roles: 4 синхронизировано»,
  «activity_log: 427 записей», «ИМПОРТ ЗАВЕРШЁН». Схема таблиц создастся сама
  при первом обращении (флаг-файл `api/.schema_ok`).
- ВАЖНО: после успешного импорта удалить папку `api/_import/` (в ней пароли ролей
  открытым текстом из экспорта).

## 8. Смоук-тест на боевом
- Открыть https://manufacture.varka.kz — грузится, в консоли «[API] сервер доступен».
- Войти каждой ролью (пароли — прежние, из экспорта): admin, operator, варщик, приёмка.
- Проверить: список партий/рецептов виден; создать тестовую правку и убедиться,
  что после перезагрузки она на месте (значит запись в MySQL идёт).
- Зайти в Админ-панель → Журнал действий: записи видны; неверный вход виден в журнале.
- Открыть роль в редакторе: поле пароля пустое с подсказкой; сохранить роль,
  не вводя пароль → войти под ней снова (пароль не должен сломаться).

## 9. Фиксация деплоя
- Сверить, что развёрнута нужная версия: `git rev-parse HEAD` на сервере ==
  последний коммит ветки (см. Tracker PROJECT_RULES §11a — не верить «задеплоено» на слово).
- Только после зелёного смоука — сообщить сотрудникам, что система переехала.
  Старый Firestore-адрес больше не использовать (данные там останутся как холодный бэкап).
