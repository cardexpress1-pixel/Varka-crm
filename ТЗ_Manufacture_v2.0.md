## 1. Назначение проекта

Manufacture — внутренняя система планирования и учёта производства бытовой
химии (варка полупродукта в реакторах → розлив/упаковка → отгрузка). Она
ведёт рецептуры, планирует загрузку реакторов и линий розлива по дням/неделям,
фиксирует фактический ход каждой варки от постановки в очередь до готовой
партии и формирует отчётность и журнал действий для одной производственной
площадки. Работает как раздел портала `varka.kz` (`varka.kz/manufacture`) с
собственным бэкендом на PHP/MySQL и собственной локальной аутентификацией для
ролей, у которых нет аккаунта на портале (цех).

## 2. Функциональные разделы

### 2.1 Backend API (`api/*.php`)

**MFG-001 — Локальный вход**
`POST api/auth.php` принимает `{login, password}`, ищет активную роль в
таблице `roles` по логину и сверяет пароль через `password_verify()` (bcrypt)
— [api/auth.php:27-31](api/auth.php#L27). При успехе создаёт серверную сессию
и возвращает `{token, role}` — [api/auth.php:40-50](api/auth.php#L40). Плохие
попытки логируются и лимитируются: 10 неудач / 15 минут с одного IP, успехи
лимит не тратят — [api/auth.php:18-25](api/auth.php#L18),
[api/storage.php:198-213](api/storage.php#L198). *(Объединяет MFG-032,
описывавший тот же механизм отдельным пунктом — см. `merged-into` там же.)*

**MFG-002 — Серверная сессия**
`createSession()` пишет токен (32 случайных байта, hex) в таблицу `sessions`
с TTL 12 часов — [api/storage.php:253-262](api/storage.php#L253).
`currentSession()` сначала ищет валидную запись в `sessions` по bearer-токену
и только при её отсутствии передаёт тот же токен в `verifyPortalToken()` как
возможный токен портала — [api/storage.php:275-284](api/storage.php#L275).
`requireAuth()` — точка входа для каждого защищённого эндпоинта: 401 без
сессии, 403 если нужен админ — [api/storage.php:463-476](api/storage.php#L463).

**MFG-003 — SSO-слой портала (fallback)**
`verifyPortalToken()` кэширует результат проверки в `portal_verify_cache` (TTL
60 сек) и при отсутствии в кэше делает `POST https://varka.kz/api/verify` с
тем же bearer-токеном — [api/storage.php:302-330](api/storage.php#L302).
Пускает только доступ с уровнем `!= none`; должность (`role_id`) выводится из
`job_title` портала, сопоставляется с таблицей `roles` по имени, либо берётся
из ручной карты `sso_role_map` — [api/storage.php:394-425](api/storage.php#L394).
Кэш сессии живёт 7 дней — [api/storage.php:445](api/storage.php#L445).

**MFG-004 — Доступы и уровни (viewer/manager/admin)**
Две независимые характеристики: `role_id` (должность → какие вкладки видно) и
`level` (`viewer`/`manager`/`admin` → что можно делать) —
[api/storage.php:370-377](api/storage.php#L370). Локальные (не-SSO) сессии
уровня не имеют: админ → `admin`, остальные → `manager` —
[api/storage.php:57-61](api/storage.php#L57). `api/sso_users.php` (только
админ) отдаёт и принимает карту «сотрудник портала → должность/уровень» в
таблице `sso_role_map` — [api/sso_users.php:20-81](api/sso_users.php#L20).
`api/roles.php` (только админ) отдаёт список `{id, name}` всех должностей для
выбора в карточке сотрудника на портале — [api/roles.php:14-17](api/roles.php#L14).

**MFG-005 — Выход**
`POST api/logout.php` удаляет запись токена из `sessions` (реальная
инвалидация на сервере) — [api/logout.php:8-11](api/logout.php#L8).

**MFG-006 — «Кто я» (whoami)**
`GET api/whoami.php` возвращает объект `role` по текущей сессии — для SSO,
где нет пары логин/пароль на клиенте. Админ-вкладка виден только при
`level === 'admin'`; для SSO без локальной роли-должности отдаётся
синтетический набор вкладок (все, кроме `admin`, если уровень не admin) —
[api/whoami.php:12-62](api/whoami.php#L12).

**MFG-007 — Синхронизация состояния приложения**
`GET api/state.php[?rev=N]` → `{rev, data}` либо `{rev, unchanged:true}`, если
присланный `rev` совпал с текущим (экономия трафика при фоновом опросе) —
[api/state.php:11-24](api/state.php#L11). `POST {baseRev, data}` → `{rev}`
либо `409 {rev, data}` при конфликте версий (оптимистичная блокировка,
`SELECT … FOR UPDATE`) — [api/state.php:51-63](api/state.php#L51). Уровень
`viewer` не может сохранять — [api/state.php:35-39](api/state.php#L35). Роли
из присланного `state.roles` синхронизирует только админ
(`syncRolesFromState()`, хеширует пароли bcrypt, вырезает их из JSON, требует
хотя бы одну роль с доступом к `admin`) — [api/state.php:68-72](api/state.php#L68),
[api/storage.php:507-568](api/storage.php#L507); для не-админа `state.roles`
подменяется авторитетной копией из БД — [api/state.php:71](api/state.php#L71).
**Лимит частоты — реализовано 2026-08-25** (решение владельца принято на
аудите «День 0», в тот же день закодировано): стартовый лимит **100
запросов/мин на сессию** на `POST api/state.php` —
[api/state.php:66-78](api/state.php#L66). Переиспользует существующий
механизм `failedAttempts()`/`recordFailure()`
([api/storage.php:198-213](api/storage.php#L198), написан изначально для
лимита неудачных попыток входа) с новым бакетом `state-write`; ключ —
bearer-токен сессии, не IP (эндпоинт авторизованный, не анонимный).
Стандартное стартовое значение платформы — `03_SECURITY_AND_PLATFORM_PLAYBOOK.md`,
«О числовых значениях»; находкой (02 Spec Audit, Шаг 3) было отсутствие
лимита как такового при том, что ТЗ уже описывало его как принятое
решение — конкретное число осталось решением владельца, не константой
методологии. Клиентский debounce 600мс (`saveState()`,
[index.html:3168-3169](index.html#L3168)) — это UX-оптимизация («не
бомбить сервер при быстром вводе»), не защита от злоупотребления, и не
заменяет серверный лимит: debounce обходится прямым запросом к API в обход
`index.html`. Живой тест (изолированный, без БД, см. отчёт 02 Spec Audit
Проход Б) — 105 вызовов одной сессией → 100 пропущено / 5 отклонено с 429;
другая сессия не блокируется чужим лимитом; 20 легитимных вызовов с
интервалом — ни один не заблокирован.

**MFG-008 — Журнал действий**
`GET api/activity.php` (только админ) — последние 200 записей —
[api/activity.php:9-13](api/activity.php#L9). `POST` — добавляет запись;
автора (`userId/userName/role`) сервер берёт из сессии, клиентские значения
игнорируются — [api/activity.php:20-33](api/activity.php#L20). Хранится как
JSON-строка в `activity_log`, ротация до последних 5000 строк с вероятностной
частотой ~19% на каждый неуспешный логин — [api/storage.php:235-248](api/storage.php#L235).
**Лимит частоты — реализовано 2026-08-25** (тот же принцип и механизм, что
MFG-007, отдельный бакет `activity-write`): стартовый лимит **100
запросов/мин на сессию** на `POST api/activity.php` —
[api/activity.php:22-29](api/activity.php#L22). Живой тест подтвердил, что
бакет `activity-write` независим от `state-write` — исчерпание лимита на
`state.php` не блокирует `activity.php` для той же сессии.

**MFG-009 — Отчёт для дашборда портала**
`GET api/report.php` (требует авторизации — любая валидная сессия) отдаёт
обезличенные агрегаты (без имён, логинов, рецептур, журналов) за диапазон
`?from&to`: количество варок/статусов, «пульс» (сварено тонн, выпущено,
загрузка реакторов, ожидает розлива) — [api/report.php:14-145](api/report.php#L14).
Повторяет логику стадии варки (`getBatchStage`) из клиента.
**Верхняя граница диапазона — реализовано 2026-08-25** (решение владельца
принято на аудите «День 0», в тот же день закодировано): диапазон `?from&to`
не может превышать **400 дней** —
[api/report.php:80-88](api/report.php#L80), явная ошибка `400 Bad Request`
при превышении, не тихое обрезание. `resolveDate()`
([api/report.php:68-74](api/report.php#L68)) по-прежнему отвечает только
за формат и «не в будущем» — проверка размера диапазона теперь отдельным
шагом после неё. Живой тест: диапазон 401 день → отклонён (400); диапазон
399 дней → пропущен. Отдельно зафиксирован факт (не изменился): клиент
Manufacture (`index.html`) этот эндпоинт вообще не вызывает — в полном
списке эндпоинтов, которые дёргает `apiFetch()`/`fetch()` (`/ping, /auth,
/state, /activity, /logout, /sso-users, /branding, /whoami`), `/report`
отсутствует; вызывающая сторона — портал, вне этого репозитория.
Ограничение диапазона поэтому превентивное, не привязано к найденному
сценарию использования/злоупотребления — фактическую потребность портала
в диапазоне шире 400 дней (если такая есть) стоит проверить отдельно, уже
после того как ограничение включено.

**MFG-010 — Брендинг (логотип)**

**MFG-011 — Health-check**

**MFG-012 — Разовый импорт из Firestore-экспорта**
`php api/import.php <dir> [--force]`, только CLI. Ждёт `varka_state.json` и
(опц.) `activityLog.json`; роли обрабатывает той же `syncRolesFromState()`, что
и штатное сохранение; без `--force` не даст затереть уже заполненный

миграции, не часть штатного потока данных приложения.

## 5. Известные архитектурные отклонения от платформенной модели

Зафиксировано как факт, без оценки и без предложения решения — решение по
каждому пункту вне рамок этой реконструкции.

1. **Локальный логин первичен, портальный токен — fallback.**
   `currentSession()` сначала ищет валидную запись в собственной таблице
   `sessions` (создаётся локальным `POST api/auth.php`) и обращается к
   `verifyPortalToken()` только если локальной сессии по этому токену не
   нашлось — [api/storage.php:275-284](api/storage.php#L275). Это не «портал —
   единственный источник личности с локальным входом только как fallback», а
   наоборот.

2. **Собственная таблица пользователей с bcrypt-паролями.**
   `roles.password_hash` хранит bcrypt-хеш локального пароля, проверяемый
   `password_verify()` в `api/auth.php:31`; таблица `roles` — полноценная
   локальная модель пользователей (логин, пароль, статус active/blocked) —
   [api/storage.php:126-140](api/storage.php#L126).

3. **Собственный экран входа существует и обязателен для части ролей.**
   Роли `warshchik` и `intake` — локальные должности без аккаунта на портале
   (по [tasks/lessons.md](tasks/lessons.md), факт зафиксирован сессией
   2026-07-29 при разборе инцидента простоя цеха); для них штатный редирект на
   портал — тупик, поэтому существует отдельная точка входа `?shop=1`
   (MFG-033) как обязательный, а не запасной путь.

4. **Двойная модель прав (должность + уровень).** Должность (`role_id`, что
   человек видит) и уровень (`level`, что может делать) — два независимых
   измерения, уровень для SSO-сессий хранится в `sso_role_map`, для локальных
   — не хранится вовсе и выводится из `is_admin` — [api/storage.php:33-61](api/storage.php#L33).
   Не проверялось, совпадает ли эта модель с моделью прав, принятой на
   платформе в целом (документ платформы не читался в рамках этой задачи).

5. **Третье место хранения сессионного материала —
   `sessionStorage['varka_session']`** (найдено 02 Spec Audit, Шаг 4.6;
   не пароль, но ранее не упомянутая локация токена сессии, помимо
   `roles`/`sessions` в MySQL). Запись при входе —
   [index.html:3517](index.html#L3517): `sessionStorage.setItem('varka_session',
   JSON.stringify({...currentUser, token: authToken}))`. Восстановление
   при загрузке страницы — `tryRestoreSession()`,
   [index.html:3646-3663](index.html#L3646): читает токен и `roleId` из
   `sessionStorage`, если не истёк локальный TTL (12ч), без обращения к
   серверу; реальную проверку токена делает первый последующий запрос.
   Очистка — при выходе ([index.html:3554](index.html#L3554)) и при
   истёкшей/отозванной сессии ([index.html:4149](index.html#L4149)).
   `document.cookie` для авторизации не используется — токен передаётся
   только заголовком `Authorization: Bearer`.

### 5.1 Конфликтные сценарии (проверено, аудит «День 0», 2026-08-25)

Поведение на границах жизненного цикла данных — проверено фактически,
зафиксировано как подтверждённые сценарии для справки при проектировании
дальнейших правок, не как открытые риски.

**Удаление роли.** `syncRolesFromState()` удаляет сессии удаляемой роли ДО
удаления самой роли, в правильном порядке —
[api/storage.php:534-541](api/storage.php#L534): сначала `DELETE FROM
sessions WHERE role_id NOT IN (...)`, затем `DELETE FROM roles WHERE id
NOT IN (...)`. `activity_log` денормализован по имени роли на момент
записи (`roleName` берётся из таблицы в момент действия,
[api/activity.php:25-33](api/activity.php#L25)); FK/каскада на `roles.id`
в схеме нет — таблица хранит запись целиком как JSON-текст
(`activity_log.entry MEDIUMTEXT`). Осиротевшая ссылка на удалённую роль в
старых записях журнала не влияет на работу системы — это текст, а не
внешний ключ. **Проверенное безопасное поведение, не риск.**

**Удаление клиента.** `state.clients[]` — плоские строки без FK
(`removeClient(i)`, [index.html:7996-8001](index.html#L7996):
`state.clients.splice(i,1)` + чистка из `wpClients`). `requests[]` и
`batches[]` хранят собственную копию имени клиента, записанную в момент
создания записи — не ссылку на список `state.clients`. Удаление клиента из
списка не может повлиять на уже существующие заявки/партии ни при каких
обстоятельствах: связи, которую можно было бы разорвать, не существует в
принципе (эффект удаления — только то, что имя больше не предлагается для
НОВЫХ записей). **Проверенное безопасное поведение, не риск.**

### 5.2 Открытые технические решения

Раздел обязателен по методологии (`PROJECT_STARTUP_PROTOCOL.md`, Фаза 2) —
ранее в документе отсутствовал, добавлен на Ш4.

этой сессии, метод — тот же, что для §6 находки) и **в тот же день
закрыта вторым фиксом** для 4 из 5 ключей — карта `STATE_KEYS_DROP_BY_ROLE`,
[api/state.php:21-31](api/state.php#L21): `clients` вырезан для
`warshchik`/`intake`/`viewer`, `workdayHours` — для `warshchik`/`intake`,
`reactors` — для `intake`, `pouringLines` — для `warshchik`. Живой тест
(изолированный, без БД) подтвердил все 5 ролей по отдельности.

**Остаётся открытым только `state.batches`** — и не по недосмотру, а
по установленной причине: `warshchik` и `intake` рендерят обзорную
панель по **всем** реакторам/линиям сразу, не только «своим» —
```js
tabsEl.innerHTML = state.reactors.map((r,i) => {
    const countToday = ... state.batches.filter(b => b.reactor === r && ...).length;
    ...
}).join('');
```
[index.html:6150-6167](index.html#L6150) (для `warshchik`, цикл по всем
реакторам) и зеркально
[index.html:6440-6450](index.html#L6440) (для `intake`, цикл по всем
линиям розлива) — обеим ролям нужен близкий к полному массив `batches`
для этой панели, простое исключение ключа (как для `requests`/`recipes`)

делает для портала) вместо урезания самого массива `batches`. Решение —

   Раздел визуально полнофункционален (поле + кнопка «Сохранить»), но
   технически ничего не подключает. Статус — предположительно
   «UI подготовлен, интеграция не реализована», не проверено дополнительным

   зафиксирован владельцем как «Этап 2» — реализовывать, остаётся в плане,
   не отменяется** (MFG-030).

2. **`roles.email` и `roles.telegram_chat_id`.** Колонки существуют в схеме

3. **[ЗАКРЫТО 2026-08-25, коммит `69641e1`] Страница «Заявки клиентов»
   (`page-requests`, MFG-016).** Статус меняется с «неопределён» на
   «закрытая находка безопасности» — это больше не архитектурная
   неопределённость, а подтверждённая и исправленная находка (см.
   `FINDING_orphaned_zayavki_page.md`, разделы 1-4 и 7). История пункта не
   удаляется, сохранена ниже.

   *Исходное наблюдение (не изменено, остаётся фактом разметки):*
   Разметка и обработчики фильтра существуют, `state.requests[]`
   заполняется и читается в других местах (модель заявки), но раздел

   соответственно, в `getEffectiveTabs()` — единственном источнике пунктов
   сайдбара ([index.html:7857](index.html#L7857)). Ни одного вызова
   `showPage('requests', …)` не найдено — раздел недостижим штатной
   навигацией ни для одной роли, включая admin. Не проверено: есть ли
   прямой вызов `showPage('requests')` из места, не найденного при этом
   поиске (полный `index.html` построчно не читался).

   *Что изменилось:* до 2026-08-25 отсутствие пункта меню было
   ЕДИНСТВЕННОЙ преградой — `api/state.php` отдавал ключ `requests`
   целиком любой валидной сессии, то есть данные были доступны в обход
   меню через консоль браузера (подтверждено живым тестом под тремя
   ролями — `warshchik`, `intake`, `operator`). Фиксом 2026-08-25 —
   [api/state.php:17,29](api/state.php#L17) — ключ `requests` вырезается

   технически по-прежнему существует (JS-функция не менялась), но данных
   там больше нет — сервер их не отдаёт. Осиротевший UI-код
   (`page-requests`, `renderRequests()`, `filterRequests()`) остаётся как
   технический долг, за рамками этого фикса.
