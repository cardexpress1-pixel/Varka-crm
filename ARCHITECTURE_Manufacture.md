фактический путь записи данных этого экрана.

**REQ-ID вне 7 модулей выше** (для полноты покрытия — не входили в заданную
структуру, не проигнорированы):

## 4. Известные отклонения от целевой архитектуры платформы

Сведено, не продублировано — источник текста в каждом случае ТЗ или этот
документ, здесь только перечень со ссылками.

- Локальный вход первичен, портальный токен — fallback (ТЗ §5 п.1 / A3 выше).
- Собственная таблица пользователей с bcrypt-паролями, свой экран входа
  (ТЗ §5 п.2 / A4.1, A8 выше). **Подтверждено как принятое временное
  исключение (owner-решение 2026-08-27), не «незамеченная проблема»**:
  `warshchik`/`intake` используют тот же локальный вход, что и
  `admin`/`operator` — одна функция `doLogin()`, одна таблица `roles`,
  разделения на «основной»/«урезанный» механизм в коде нет, и у этих двух
  ролей нет портальных аккаунтов. Удаление локального входа сломает обе
  категории ролей одновременно (прецедент — инцидент простоя цеха
  2026-07-29, `tasks/lessons.md`). Три пути решения на будущее и полный
  текст — `TRACEABILITY_Manufacture.md` §4 п.3.
- Отдельная обязательная (не запасная) точка входа `?shop=1` для ролей
  `warshchik`/`intake`, у которых нет аккаунта на портале (ТЗ §5 п.3).
- Двойная модель прав: должность (`tabs`/`fields`) + уровень (`level`)
  как два независимых измерения (ТЗ §5 п.4 / A4.2 выше).
- Путь на едином домене вместо поддомена с отдельным document root
  (A1 выше).
- Комментарий `api/config.php.example:10` ссылается на
  `PLATFORM_ARCHITECTURE.md` — документ, отсутствующий в текущей
  методологии (уже зафиксировано и заменено в `METHODOLOGY_REVIEW.md`,
  находка №8, на `PLATFORM_INTEGRATION_PROTOCOL.md` +
  `PLATFORM_CONTEXT_varka.md`). Комментарий в коде отстал от ревизии
  методологии — не архитектурная проблема Manufacture, техническая
  уборка на будущее, не блокирует Ш4.
- **`CLAUDE.md` не содержит моста ТЗ↔модули** — весь мост (REQ-ID →
  модуль → путь в репозитории) существует только в этом документе
  (`ARCHITECTURE_Manufacture.md`); `CLAUDE.md` (governance) ни разу не
  упоминает ни один REQ-ID, ни один файл `api/*.php`, ни одну секцию
  `index.html` — только процесс деплоя/веток/данных. Находка для будущего
  Ш5 (переписывание `CLAUDE.md` по шаблону методологии), не блокирует Ш4.

**Явно зафиксировано:** часть перечисленных отклонений — это решения,
принятые **до** появления текущей версии методологии (в частности,
переход платформы на путь одного домена датирован 2026-07-11 —
`api/config.php.example:10-11`, `CLAUDE.md`), а не ошибки, допущенные в
рамках текущей сессии аудита. Не переоценивать их задним числом как
«упущенные при разработке» — на момент принятия решений действующей
методологии в этом виде могло не быть.

## 5. Открыто, требует диагностики платформы (не проекта)

Закрытие этих пунктов зависит от Ш0 (`PORTAL_DISCOVERY_PROTOCOL.md`),
выполняемого на стороне портала — не от доработки кода Manufacture:

- **A5** — где в портале появляется ссылка на модуль Manufacture → блок
  **D3** «Реестр модулей в портале».
- **A6** — нужны ли уведомления Telegram и через какого бота → колонка
  `roles.telegram_chat_id` существует, но её потребитель (если будет)
  определяется решением по платформенному Notification Service, не этим
  репозиторием.
- **A9** — audience-идентификатор, который обязан проверяться в
  `verifyPortalToken()` → блок **D6** «Контракт `https://varka.kz/api/verify`».
